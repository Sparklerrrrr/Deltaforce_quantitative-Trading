### 几个需要你知道的设计决定

- **止损线的处理**（你让我设计）：一个品种在 moligod 只有高、低两个阈值。空仓时“低于线 = 买入线”；
  你记账买入后，下一次 `mail-poll` 会把它换成“止损线”，高于线始终是卖出线（且不低于持仓回本价）。
  代价是：从你买入到回复邮件之间，低于线仍是买入线。所以邮件里每条买入指令都直接写了止损价。
- **邮件记账的四道关**（第二轮审查后加固）：发件人地址 → 邮箱服务商的 SPF/DKIM/DMARC 验证结论 →
  必须是对计划邮件的回复 → 按那份计划是模拟还是真实记入对应账本。任何一关不过都不记账。
  From 地址和回复关系都能伪造，所以单凭它们不算数。邮件内容只被解析成成交记录，不会被当作指令。
- **两本账**：模拟计划的成交只进模拟账本，真实计划的只进真实账本。真实持仓、余额、盈亏和实盘风控
  只看真实账本。归属在发计划邮件时记入本地数据库，不看回复里写了什么。
- **`--dry-run` 的含义**：不花接口次数（只读缓存）、不发邮件、不改 moligod、不记决策。想看完整效果用 `--mock`。
- **接口次数的记法**：每个发出的请求都计次，包括重试。平台有的接口是“成功才扣”，所以程序显示的数字只会多不会少。

## 六、已知风险和限制

1. **冷启动**：分钟曲线只有 24 小时，头几天阈值是按日线估算的（邮件里会标“冷启动”“可信度较低”）。
   连续运行 3 天后才开始用分钟分位，7 天后稳定。**某晚没跑，那 24 小时的分钟数据就永久缺失**，
   复盘时会退化成用日线高低点判断。
2. **“触线即成交”不等于真能成交**：复盘用的是平台的参考价。真实交易行有挂单量、排队、价格跳档，
   你未必能按买入线买到足量。模拟盈亏因此偏乐观，真实表现以你记账的成交为准。
3. **第三方接口**：小涛查是付费第三方，可能改字段、改扣次规则、停服。程序对结构变化有容错，
   但字段含义变了它不会知道。接口文档里同一子弹在不同示例中 oid 不同，说明 ID 可能变过。
4. **moligod 页面改版**：元素名称一变同步就会失败。失败只会回退到手动清单，不会乱点。
   另外请留意它的用户协议——“低频设置自己的提醒”是你的判断，自动化操作本身是否被允许，我无法替你确认。
5. **邮件**：QQ 邮箱的授权码会过期。邮件记账依赖邮箱服务商在邮件头里写入 SPF/DKIM/DMARC 验证结论，
   **QQ 邮箱（尤其是自己发给自己时）到底写不写、标识是什么，我没有实测过**；不写的话邮件记账用不了，只能命令行记账。
   某些邮件客户端回复时会丢掉引用关系，那样的回复会被拒绝并回信说明。
6. **规则基线很朴素**：就是分位数。它不懂版本更新、不懂活动。大模型能补一部分，但模型的调整是否有用，
   只有 `perf` 里“最终建议 vs 规则基线”那一行能回答。
7. **关键词观点提取很保守**：没开大模型时，只识别“提到品种 + 明确涨跌用词”的句子，会漏掉委婉的说法。
8. **资金安全**：默认 `paper_mode: true`。系统的任何建议都可能是错的，它没有在真实行情上被验证过一天。

## 七、一个比代码更重要的发现：止损非常贵

第一版规则基线在模拟数据上跑出了这样的结果：**止盈占比 65%，但单笔平均亏 4.9%**。

查明细后原因很简单，而且是**与数据无关的算术**：

| 结果 | 单笔扣费后收益 |
|---|---:|
| 止盈（卖出线只比回本价高一点） | +2% ～ +3% |
| 止损（买入线下方 8%，再扣 13% 卖出费） | **−20%** |
| 到期没卖掉，按当时清算 | −15% ～ −19% |

也就是说，**一次止损要 8 次止盈才能填平**。在 13% 的费率下，“跌 8% 就止损”不是保护，而是把账面浮亏变成 20% 的实亏。

我据此改了三处默认设计：

1. 止损线 = 取“买入线 × 0.9”和“近期最低价 × 0.98”中**更低**的那个。
   止损只在价格跌破近期所有低点时触发——那代表行情结构变了（比如版本削弱），而不是日常波动。
2. 最低利润率从 2% 提到 3%。
3. 邮件里每条买入指令都直接写出“触发止损则实亏约 −22%”，让你下单前看到真实代价。

改完后同样的模拟数据：14 晚只发出 15 个买入信号、触发 2 个、0 次止损。信号少了很多，但不再被止损吞掉。

**请注意这个结论的边界**：算术对真实行情成立；但“改完之后能不能赚钱”我不知道。
模拟数据是我造的（日内振幅 5%～10%，刚好在盈亏线附近），在它上面调参没有意义，我也没有继续调。
真正决定这类策略成败的问题只有一个：**真实子弹的“低分位到高分位”价差，是否稳定地超过约 17%
（13% 费率 + 3% 最低利润）？** 文档示例里有的物品日内高低点相差很大，但那不是证据。
这个问题只有你的真实数据能回答，而且一两周就能看出来——`python -m dfq status` 和每晚邮件里的“观望：空间不足”
会直接告诉你有多少品种过得了这条线。如果长期没有品种过线，说明该换品种（低等级弹？）或这条路本身走不通，
那也是一个有价值的、省钱的结论。

## 八、下一步建议

1. **先跑 probe，把实测报告给我。** 这是唯一阻塞正确性的事。
2. **模拟模式连续跑满 7 天**，不要中断。重点看：有多少品种能过“空间不足”这一关；买入线的触发率。
3. **重新考虑关注清单。** 默认的 8 个都是 5 级弹，是我从文档示例里随手选的常见型号，不是基于数据的选择。
   probe 之后可以用一晚的列表数据看哪些品种日内振幅最大，那才是该关注的。
4. **数据满一周后再开大模型**，这样“最终建议 vs 规则基线”的对比才有意义。之前开只是在花 token。
5. **认真对待 `perf`。** 如果攒够 20～30 笔触发后，最终建议既不优于规则基线、也不优于什么都不做，
   那就该停下来改策略，而不是继续跑。这是你在提示词里定的“唯一标准”，我认为它是对的。
6. 之后可以做的改进（等有真实数据再说）：按品种分别调参；用小时曲线的平台预测做对照信源；
   把“昨日最高收益”接口的结论转成可打分的观点；持仓超过 N 天的处理规则。

## 九、第二轮代码审查的修复（PR #1 追加提交）

审查提出的五个问题逐条核实后都属实。下面是每一项改了什么、怎么测的、还剩什么风险。
**同样的声明：这些修复只用假对象、本地文件和本机回环地址测过，没有连过真实邮箱、真实模型接口或 moligod。**

### 1. 模拟成交会被记进真实账本（已修复，优先级最高）

- **问题**：邮件记账写死了 `paper=False`。回复【模拟计划】邮件的成交会变成真实持仓，
  进而影响真实余额、风控上限和下一份计划里的卖出指令。
- **修复**：
  - 每封发出的计划邮件都在本地数据库里记下“这份计划是模拟还是真实”；回复记哪本账只以这条记录为准，
    不看邮件标题和正文怎么写，也不受你之后修改 `paper_mode` 的影响。
  - 对不上任何计划的回复（新写的邮件、回复的是测试邮件等）**拒绝记账**并回信说明，不再默认当真实成交。
  - 持仓、余额、当日投入、已实现盈亏的每个查询都必须指明看哪本账。实盘计划的风控只看真实账本，
    模拟计划只看模拟账本，互不渗透。`status` 和 `perf` 把两本账分开列出。
- **测试**（14 个）：模拟回复后真实账户的 9 项状态逐一比对不变；归属不受邮件文字影响；
  三种“对不上计划”的情况都不记账；完整链路（模拟计划 → 回复 → 次日再跑 → 切到实盘）；旧数据库迁移。

### 2. 邮件身份验证（已加固）

- **问题**：只核对了 From 地址和 In-Reply-To，这两样都是发信人自己填的。
- **修复**：记账前必须有你的邮箱服务商给出的 SPF / DKIM / DMARC 通过结论，且通过的域就是你的邮箱域。
  只采信配置里指定的服务商标识写的、并且是最靠上的那一条验证结果（发信人可以伪造这个邮件头，
  但伪造的只能排在服务商那条的下面）。From 里出现多个地址的直接拒绝。
  身份没确认的邮件不记账、也不回信。计划邮件的编号改用 128 位随机数。
- **测试**（49 个）：伪造发件人 + 已知邮件编号但无验证结论；验证失败；别的域通过了验证；
  自己塞一个“验证通过”的头；冒用服务商标识；多个 From；无效的回复关系；未配置时全部拒绝。
- **你需要做的**：填 `mail.auth.trusted_authserv`（第四节第 6 步）。**没填之前邮件回复一律不记账。**

### 3. 大模型 API 的安全传输（已修复）

- **问题**：`llm.base_url` 填 `http://` 也照发，API Key 会明文传输。
- **修复**：只允许 `https://`。唯一例外是本机回环地址（`localhost` / `127.0.0.1`），
  且要显式打开 `llm.allow_http_local`；局域网地址不算本机。底层请求函数再查一遍，
  所以小涛查 token、新闻搜索 Key 也受同一规则保护。不再跟随重定向（标准库跟随时会把密钥头带到新地址）。
  Key 被登记进脱敏表，即使服务端把它原样写进报错正文，日志和异常里也不会出现。
- **测试**（38 个）：各种 http / https / 本机 / 局域网 / 形似本机的地址；Key 不出现在异常、日志、
  流水线提示和邮件里；起了一个本机测试服务验证重定向确实没被跟随。

### 4. 配置校验（已重写）

- **问题**：只检查了 4 项。比例写成 `5`、键名拼错都不会报错，风控可能悄悄失效。
- **修复**：每个配置项都有类型和取值范围；不认识的键直接报错并给出拼写建议；
  布尔值、字符串、NaN、无穷大不能冒充数字；检查参数之间的关系；所有问题一次列全并拒绝运行。
  `overrides.yaml` 里超范围或不在白名单内的条目从“悄悄忽略”改成报错。
  流水线里不允许去掉或关闭护栏节点，也不允许把它排到模型之前。
  命令行记账、设余额和邮件记账的数量 / 价格也加了有限性和上限检查。
- **测试**（175 个，多数是参数化的边界值）。

### 5. 提示词注入（已加固，但请注意它的边界）

- **问题**：文稿、新闻原样拼进提示词，里面写一句“忽略以上规则”就可能影响模型。
- **修复**，三层：
  1. **隔离**：系统指令和外部文本分开放；外部文本只在一对带随机编号的标记之间，并明确告诉模型那是数据。
  2. **筛查**：明显在对模型下指令的文稿整篇隔离——不给模型看、不产生观点、不进入分析，并在邮件里告诉你。
  3. **兜底**：模型的输出仍然必须过代码护栏。这次额外补了一条：模型不能把止损线设得比规则止损线更紧。
  另外，模型写的理由和摘要在进入邮件前会去掉链接、邮箱和换行，防止被注入后生成钓鱼内容或伪造邮件小节。
- **测试**（76 个）：12 种注入写法被筛出、6 种正常文稿不被误伤；
  并且**假设前两层全部失守、模型完全照攻击者的意思输出**，验证仓位上限、回本价、止损范围、
  品种范围、配置都没有被突破。
- **边界**：第 2 层是关键词规则，**挡不住措辞隐蔽的注入**，也可能误伤正常文稿。
  它只是减少暴露；真正的保证来自第 3 层。在护栏允许的范围内（阈值 ±10%），
  被误导的模型仍然可以给出更差的建议——这要靠 `perf` 里“最终建议 vs 规则基线”来发现。

### 尚未解决的风险

1. **邮件身份验证依赖邮箱服务商**。QQ 邮箱是否在邮件头里提供验证结论、对自己发给自己的邮件是否提供，未实测。
   如果不提供，邮件记账功能不可用（这是有意的：宁可不能用，也不在无法确认身份时记账）。
2. **验证标识要你自己确认**。`trusted_authserv` 填错（比如填成了攻击者邮件里出现的标识）会让验证形同虚设。
   只应填你确认属于自己邮箱服务商的那个。
3. **邮箱本身被盗**不在防护范围内：能登录你邮箱的人可以发出一切验证都通过的邮件。影响限于记假账，不会触发任何交易。
4. **提示词注入不能根除**，见上面第 5 项的边界。
5. **本机数据库和配置文件没有防篡改**。能改你电脑上文件的人可以改账本、改配置。这超出了本程序的范围。
6. **命令行记账默认记真实账本**。模拟模式下忘了加 `--paper` 会记到真实账本里（程序会提示，但不会阻止）。
7. 第一轮报告里列出的全部“未实测”项目依然未实测：小涛查接口、SMTP/IMAP、大模型接口、moligod、Windows 计划任务。
