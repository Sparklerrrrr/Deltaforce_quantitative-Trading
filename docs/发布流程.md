# 发布流程（给维护者）

> 现状（2026-11-21）：`.github/workflows/ci.yml` 和 `.github/workflows/release.yml` 已写好，但**还没有在 GitHub 上实际运行过**。
> 第一次发布时请盯着 Actions 页面的日志，按实际情况调整。

## 一句话

改 `dfq/__init__.py` 里的版本号 → 合并到 `main` 且 CI 全绿 → 打 `v版本号` 标签并推送 → GitHub 自动构建、验收、扫描、算校验值，
生成一个**草稿** Release → 你核对后点“发布”。

为什么由 GitHub 构建而不是在自己电脑上构建：干净的机器、干净的检出，安装包里不可能混进你自己的 `config.yaml`、`.env`、`data/`；
构建记录（提交号、依赖版本）自动留档，别人可以核对安装包对应哪一份源码。

## 每次发布的步骤

1. **改版本号**：`dfq/__init__.py` 的 `__version__`（和 `pyproject.toml` 的 `version` 保持一致），在 `CHANGELOG.md` 写这一版改了什么。
2. **合并到 main**，等 CI 全部通过：
   - `test`：Windows × Python 3.11 / 3.12 / 3.13 / 3.14 跑全部测试；
   - `lint`：ruff（只查真正的错误）、vermin（确认 3.11 能跑）、mypy；
   - `audit`：pip-audit 查依赖的已知漏洞；
   - `secrets`：`scan_secrets.py --tree --history`，扫当前文件和完整 Git 历史；
   - `installer`：构建安装包并运行 `scripts/release_test.ps1 -SkipGui`。
3. **打标签并推送**（标签必须等于 `v` + `__version__`，否则工作流直接失败）：
   ```powershell
   git tag v1.0.1
   git push origin v1.0.1
   ```
4. **等 Release 工作流跑完**。它会依次：核对标签与版本号 → 跑测试 → 扫描源码和完整历史 → 准备 Inno Setup →
   用 `scripts\build_exe.bat` 构建（与本地构建是同一个脚本）→ 扫描打包目录 → 运行验收脚本 → 生成 `SHA256SUMS.txt` 和 `build-info.txt` →
   创建**草稿** Release。Release 上**只附安装包** `DFQ-Setup-x.y.z.exe` 一个文件，SHA-256 校验值写在 Release 说明里。
   下面这些构建记录不附到 Release 上，而是保存在这次工作流运行的 Artifacts 里（`release-record-vx.y.z`，保留 90 天），供维护者核对：
   | 文件 | 内容 |
   |---|---|
   | `SHA256SUMS.txt` | 安装包的 SHA-256 校验值（`sha256sum` 格式） |
   | `build-info.txt` | 标签、提交号、工作流运行链接、构建时间与系统、Python 和 Inno Setup 版本、构建用的全部 Python 包版本 |
   | `release-test.txt` | 验收脚本的完整输出（PASS / FAIL / SKIP） |
   | `scan-repo.json`、`scan-dist.json` | 源码 + 历史扫描、打包目录扫描的结果（已打码） |
5. **人工核对草稿**：
   - `release-test.txt` 最后一行 `0 failed`；SKIP 的只有需要桌面会话的项；
   - 两个扫描结果里“疑似真实”为 0；
   - `build-info.txt` 里的提交号就是你要发布的那个；
   - 在一台真实的 Windows 10 / 11 上下载安装包，按 [安装说明](安装说明.md) 核对校验值，然后运行
     `powershell -ExecutionPolicy Bypass -File scripts\release_test.ps1 -Setup <下载的安装包> -Dir $env:TEMP\dfq-rt`
     （不加 `-SkipGui`，补上窗口、首次启动生成配置、单实例、WebView2 这些 CI 测不了的项）。
6. 都没问题就在 GitHub 上把草稿**发布**。有问题就删掉草稿和标签，修好后用新的版本号重来（不要复用已经推送过的标签）。

## 验收脚本 `scripts/release_test.ps1`

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\release_test.ps1 `
    -Setup dist\DFQ-Setup-1.0.1.exe -Dir $env:TEMP\dfq-rt [-OldSetup 旧版安装包] [-ScanScript scripts\scan_secrets.py] [-SkipGui] [-SkipTasks]
```

覆盖：全新安装不带个人文件 → 命令行模式（`DFQ.exe status`、`DFQ.exe run --mock --offline`）且不往安装目录之外写文件 →
首次打开窗口生成配置、空白 `.env`、目录和数据库，单实例 → 升级保留配置 / 密钥 / 数据（给了 `-OldSetup` 就是跨版本升级）→
计划任务的创建 → 第二个安装目录互不影响（卸载其中一个不删另一个的计划任务）→ 三种卸载模式 → 完全删除不顺着目录联接删到外面。

它会**拒绝**在已经装过 DFQ 的电脑上运行（会改掉“应用和功能”里的卸载登记），已有 `dfq-*` 计划任务时跳过计划任务一节。
请在干净的电脑、虚拟机或 Windows 沙盒里跑。

## Inno Setup 与中文语言文件

- `installer/DFQ.iss` 要求 Inno Setup **6.5 或更新**（脚本开头有版本检查）：`x64compatible` 需要 6.3+，中文语言文件按 6.5 的消息表翻译。
- 中文语言文件放在仓库里：`installer/Languages/ChineseSimplified.isl`，原样取自 Inno Setup 7.1.1 安装目录里的官方文件
  （文件头写明 “Inno Setup version 6.5.0+ Chinese Simplified messages”）。
  - SHA-256：`e0b0b350e2245f3c5e65586dfe43d574f6e7f06f2261149aba284954b3fc9a8d`
  - `.gitattributes` 里对 `*.isl` 设了 `-text`，Git 不转换它的换行，校验值才对得上。
  - 为什么放进仓库：不同机器上的 Inno Setup 不一定带中文语言文件，放进仓库后本机和 GitHub 上的构建结果一致。
  - 文件里有译者公开的联系邮箱，已登记在 `scripts/scan_allowlist.txt`（误报）。
- GitHub 的 Windows 机器上：工作流先找已安装的 Inno Setup，版本低于 6.5 或没有时用 Chocolatey 安装最新版。

## 敏感信息扫描 `scripts/scan_secrets.py`

```powershell
python scripts\scan_secrets.py --tree               # 当前跟踪的文件
python scripts\scan_secrets.py --history            # 完整 Git 历史
python scripts\scan_secrets.py --dir dist\DFQ       # 打包目录 / 安装目录
```

输出全部打码。发现“疑似真实”时退出码为 1。处理办法：

- **真的泄露了**：立刻到对应平台作废 / 重新生成那个密钥，再从文件里删掉。**不要改写 Git 历史、不要强制推送**：
  公开过的东西要当作已经被人看到，作废才是真正的补救。
- **其实是假值**：改成一眼看得出是假的写法（`dummy-test-token-0000`）；确实不能改的（例如第三方原样文件），
  登记进 `scripts/scan_allowlist.txt`，写清楚理由。
